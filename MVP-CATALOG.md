# Initial MVP detector and integration catalog

This is the proposed release scope, not a claim that the detectors already exist or that a directory name establishes disposability. M0 validates feasibility, pins supported tool versions, and freezes this catalog. Scope changes require a recorded decision and updated roadmap/tests. No detector may silently widen its roots, file patterns, or supported versions.

## Named categories

| ID | Tool / category | Discovery and evidence | Proposed MVP operation | Required exclusions / negative fixtures |
|---|---|---|---|---|
| D1 | Cargo compiler/build output | Recognized Cargo workspace; resolve target location from trusted configuration/metadata without invoking a build or project hooks; reconcile output manifests and local edits | Stage only individually substantiated generated output files or a fully verified generated subtree; retain the project | Custom target paths require explicit scope; edited/unknown files, source-like additions, shared target ownership, active builds, and unresolved provenance block the affected action |
| D2 | CPython generated bytecode | `__pycache__` entries with validated bytecode format, corresponding retained Python source, and a compatible regeneration path | Stage verified bytecode files, never a guessed whole directory | Bytecode-only modules, missing source, unknown file formats, custom files, symbolic links, environments without a demonstrated regeneration path |
| D3 | pytest execution cache | Recognized pytest project and cache ownership; allowlisted generated records with validated structure | Stage only verified cache records; keep unknown contents | Local notes, unexpected files, active tests, uncertain ownership; no deletion based solely on the `.pytest_cache` name |
| D4 | Homebrew cached package downloads | Discover roots through a validated, read-only integration; match cached artifacts to package metadata/checksums and distinguish downloadable cache from installed state | Stage verified download artifacts only when the adapter can substantiate them | Installed kegs/casks, arbitrary archives in the cache root, incomplete downloads, custom artifacts, offline-only copies the user retains, untrusted wrapper executables/configuration |
| D5 | Downloaded macOS installers | Bounded metadata inspection of selected `.dmg` / `.pkg` files; installed application/version evidence where available | Explicit per-file review and staging; owner matching is supporting evidence, not an automatic removal rule | Mounted/in-use disk images, user-created disk images, unique archives, unsupported parsing, uncertain provenance; no running installers or contained code |
| D6 | Exact duplicate regular files | Selected non-managed scopes; stable full-content verification after grouping; retained location explicitly chosen | Stage selected copies while retaining verified survivors | Hard links counted as shared storage, symlinks, cloud-only contents, managed-library internals, changing files, survivor inside another selected removal |
| D7 | Large files and folders | Metadata/coverage-based discovery in selected scopes | Explain/reveal/add to plan; execution only through a supported file/category adapter | No generic recursive deletion or inference that large means disposable; unfamiliar/managed stores remain review-only |
| D8 | Ordinary standalone Git clones | Full local-state assessment plus fresh remote/object verification and a valid authentication adapter | Stage a reviewed verified clone; permanent removal requires a second plan | Worktrees, submodules/nested repos, alternates, LFS, shallow/partial/sparse clones, unknown local state, unsupported auth, expired evidence, and verification-budget exhaustion remain blocked initially |

## Minimum useful M3 release slice

D1–D4 are the initial named generated-data/cache targets; D5–D7 complete the offline review experience. D8 is integrated in M4. M3 requires at least two executable generated-data/cache families among D1–D4, plus D6, to pass complete staging/restoration/permanent-removal tests. M0 must choose the executable subset and mark every remaining target review-only or deferred with its reason. This gate prevents the release passing with only a framework or a list of unexecutable findings.

Use representative fixture projects and manager-generated artifacts from the frozen tool/version matrix. Every family needs positive, mixed valuable/generated, unknown-version, active-use, changed-since-review, and recovery fixtures. Include at least one realistic consented pilot scope before public release; do not rely exclusively on trivial synthetic directories. Real private material remains local unless separately consented for model evaluation.

If fewer than two families are feasible, M0 does not pass the planned cleanup scope: revise the scope/forecast explicitly. A difficult detector becoming review-only must not be disguised as successful cleanup support. The plan may recommend new catalog entries later, but model judgments cannot create new executable categories at runtime.

## Git transport and authentication scope

Initial release target: public GitHub HTTPS and private GitHub HTTPS, using app-mediated credentials stored in macOS Keychain. No token in URLs, process arguments, renderer state, logs, or persisted verification configuration. Select and prove the exact transport/credential-broker implementation in M0 before committing to M4 estimates.

Public-only verification is insufficient for the Git milestone. Acceptance uses an app-owned disposable public repository and a disposable private repository with authorized test credentials, plus revoked/denied credentials and network failure. No real project needs to be pushed or modified for this test. Remote reads require consent; they are not authorized by this planning document.

SSH URLs, GitHub Enterprise, other hosts, SSH agents, repository-configured credential helpers, and custom remote transports are outside initial authenticated execution support. Show the limitation and allow the user to select an explicitly reviewed equivalent supported verification endpoint where applicable; never rewrite the source remote silently. If private HTTPS is not feasible within the chosen access model, M0 records a product-scope decision and new estimate; M4 cannot pass as originally specified by testing public repositories alone.

## Verification resource defaults

Proposed starting limits, calibrated in M0 and frozen with the adapter:

- One verification job at a time.
- At most 2 GiB of network ingress and 2 GiB of temporary storage per repository.
- At most 4 GiB across all live app-owned verification stores.
- Preserve at least 2 GiB of free space on the verification volume, plus journal/checkpoint headroom; a user's lower available space does not increase these limits.
- Five-minute wall-clock limit per attempt; no automatic repeated full fetches after a budget failure.

Preflight every attempt, enforce network byte limits in the transport, monitor temporary-volume growth and free space during the job, and account for bounded cancellation overshoot in the reserve. If the implementation cannot enforce the required limits, the adapter does not pass M0. A failed verification job may be terminated because it writes only to an isolated app-owned store, never the source clone.

Journal temporary-store ownership and cleanup intent. Delete partial stores after cancellation/failure when no live worker holds them; reconcile abandoned stores on next launch. Cached stores count toward the aggregate budget and need versioned integrity/freshness checks before reuse. Never delete an arbitrary path or source object store as cleanup. The user may choose a different local verification volume with sufficient space; the limits still apply. Inability to verify within budget produces a visible blocker, never a weaker deletion test.
