# Fixture lifecycle runtime schema v2

**Status: implemented as a bounded runtime migration; the purge lifecycle layer is implemented in `fixture-lifecycle` (batch A), the coordinator/service purge flow remains unimplemented.** New fixture sessions use schema v2. Reopening an exact valid v1 session validates the existing manifest, directory identities, five registered fixtures, and complete stage/restore attempt history before and again inside an `IMMEDIATE` transaction. The transaction rebuilds only the two CHECK-constrained tables, copies every column and `rowid` explicitly in rowid order, validates the copied registry, and updates `user_version` to 2 only after the copy and checks. Manifest data and fixture files are untouched.

The v2 CHECK constraints reserved `purge` and `permanently_removed` vocabulary for the lifecycle design. Since batch A of `fixture-purge-v1`, runtime validation accepts the purge operation's journaled states (`operation='purge'` with `intent`/`permanently_removed`/`uncertain` outcomes, `status='permanently_removed'` with its receipt) only when the complete issued-and-staged receipt history and the terminal purge journal row back them; every other reserved use stays rejected and preserved. No native command, renderer authority, or approval path exists yet.

The existing owner lease must be held by the trusted coordinator for the complete reopen/migration. Schema, manifest, fixture, and attempt validation is rerun before stage, restore, and snapshot reads. Unknown or future schemas, extra objects, malformed or oversized metadata, and invalid directory identities fail closed without reset or reseed. The migration preflight alone has a fixed 256-row maximum for historical v1 attempts, checked before materialization; this bound does not limit ordinary v2 stage/restore history. SQL count and byte caps run before row materialization.

Disposable tests build v1 databases from their own new fixture sessions. They cover empty and staged/restored history, non-contiguous rowids, restoring an old receipt after migration, transaction rollback at each rebuild checkpoint, unknown schema changes while a handle is open, and rejection of reserved purge vocabulary. No test opens installed app data; tests do not establish native startup integration or authorize production purge.
