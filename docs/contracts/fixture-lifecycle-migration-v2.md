# Fixture lifecycle v1 to v2 migration experiment

**Status: experimental proposal.** This document and `probes/fixture-migration` do not define a runtime migration, purge API, or permanent-removal operation. The primary 0.0.8 checkpoint kept the runtime on schema v1. This branch separately adopts runtime schema v2 without a purge API; its reserved purge vocabulary is still refused by runtime validation. See `fixture-runtime-schema-v2.md` for that separately tested implementation boundary.

The probe creates disposable five-file sessions through the public fixture lifecycle API. It stages, restores, and stages again to generate real manifest, fixture, receipt, and attempt rows. As the current creator now uses v2, test setup rebuilds only each self-created database into the exact frozen v1 layout, preserving rows and rowids before running the experiment. It has no command-line arguments or caller-selected paths. It performs SQLite schema changes only on those test-owned databases and never unlinks fixture or user data.

The proposed schema preserves the current manifest, fixture, and attempt columns. Its only intended CHECK changes are `fixtures.status` accepting `permanently_removed`, `attempts.operation` accepting `purge`, and `attempts.outcome` accepting `permanently_removed`. These values are vocabulary for later design discussion; this experiment does not write them.

Before changing a v1 database, the probe requires the exact current application ID, schema version, and three-table schema, with no other schema objects. It checks the public lifecycle snapshot and all bounded manifest, fixture, receipt, and attempt values. For snapshot-backed sessions, the existing lifecycle validator checks the current bindings, file content and identities; the probe also verifies each deterministic fixture digest and the historical attempt value relationships. It then rebuilds the two CHECK-constrained tables in one `IMMEDIATE` transaction and compares every old row before and after copying. A schema mismatch, unsupported version, malformed row, or injected failure leaves the database unchanged. A v2 rerun validates the exact proposed schema and rows without copying them again.

The fault tests interrupt after rename, after table creation, after row copy, and immediately before the version update. Each checks transaction rollback of schema and data and confirms the v1 layout and rows remain intact and that the current runtime can reopen them through its separately tested upgrade path. A separate test exercises both a historical `uncertain` outcome and a pending `intent` in independent test-owned databases, closes and reopens each, then checks migration preserves those records and the uncertain fixture state without a filesystem retry. This is a state simulation, not proof of behavior after a real process crash. These injected function-level failures do not establish power-loss or process-crash durability behavior for SQLite/WAL. Additional tests reject each extra view, trigger, or table independently, a future schema version, and malformed metadata without resetting or rewriting the database. A newly created valid session with no attempts is also covered.

This experiment does not establish how a real purge would be reviewed, confirmed, revalidated, authorized, interrupted, retried, restored, or accounted for. It does not establish that a row marked `permanently_removed` corresponds to an unlink or reclaimed storage. Those behaviors remain outside this contract.

Pending operation observations are checked separately from stored fixture state: a stage intent can leave the persisted fixture `available` while the public snapshot reports `Uncertain` with the intended receipt. The experiment preserves those original fields and the pending attempt; it never converts uncertainty into a completed filesystem operation.
