# M1C validation — runtime fixture schema v2 adoption

Version 0.0.9, branch `feat/m1c-lifecycle-schema`, based on `ed49cd8` (PR7, `feat/m1c-purge-schema`). This adopts the reviewed v1→v2 fixture-lifecycle schema migration into the runtime crate. It introduces **no purge API, no unlink or deletion capability, no new native command, no UI change, and no space-reclaimed claim**. Reserved future purge vocabulary (`operation='purge'`, `status='permanently_removed'`, `outcome='permanently_removed'`) exists only at the CHECK-constraint layer and remains rejected by the runtime allowlist validator.

## What changed

- `FixtureLifecycle::reopen` now migrates a legacy schema-1 fixture database in place: pre-transaction validation of exact v1 schema, manifest identity, row bounds and registry; then an `IMMEDIATE` transaction that rebuilds only the `fixtures`/`attempts` CHECK tables with explicit `rowid`, all columns and `ORDER BY rowid` preservation; `user_version=2` is committed last after full schema validation. Unknown/future schema versions and extra schema objects fail closed with no reset.
- New sessions are created directly at schema 2; stage/restore/snapshot re-run schema and registry validation per call.
- Coordinator guard: `DemoExecutionService::ready_session` refuses to lazily reopen fixtures when the owner lease is not held (`ensure_active`), because reopen may now perform a write migration. Contract `fixture-runtime-schema-v2` requires the lease for the complete reopen. Status refresh with the lifecycle handle still held stays usable after a poison, so the UI can show uncertain state.

## Open gates

- Purge primitive (0.0.10, this branch): `FixtureLifecycle::purge_receipt` implements the receipt-addressed permanent removal of exactly one staged fixture, per the frozen `fixture-purge-v1` contract's lifecycle layer. Identity re-verification (regular file, device/inode, one link, exact bytes, content digest) runs through the opened no-follow holding-directory handle — twice: before the intent is journaled and again immediately before the unlink; the unlink is directory-relative through that same handle; failures at the recheck/unlink/sync/outcome boundaries become `Uncertain`, never a success claim or a retry. The v2 reserved vocabulary is now active for purge only (`status='permanently_removed'`, attempts `operation='purge'` with `intent`/`permanently_removed`/`uncertain`); all other reserved values stay rejected. 141 workspace tests include the new vocabulary/validator, happy-path, refusal (unknown receipt/wrong state/changed identity — refused before any intent is journaled), unlink-failure uncertainty (read-only directory pin), crash-after-intent reopen (uncertain, no retry, intent row preserved), terminal-refusal/serial-exact-target, and tamper-refusal tests (a purge journal row without matching issued-and-staged receipt history fails closed on reopen; outcome journaling requires exactly one live attempt row). Two real gaps were caught and fixed: the registry cross-check previously refused to reopen a session with a pending purge intent (would brick the session after a mid-purge crash), and fabricated purge rows without stage history previously passed validation.
- Honest limits: the same-user TOCTOU between final verification and the directory-relative unlink is documented (name-bound, not inode-atomic; no portable conditional-unlink primitive) and mitigated by directory privacy, opened handles, and uncertainty reporting. A second lifecycle handle observing a snapshot mid-purge from the same process (outside the coordinator's lease design) could report `Changed` across the race window; the single lease-owning coordinator is the designed prevention, and batch B's control store formalizes it. A post-commit WAL-checkpoint failure in intent journaling returns the raw error while the intent is already durable; callers treat this exactly as stage/restore do, and any retry converges to `Uncertain` via the pending-intent guard. Subprocess-boundary crash tests, approval-ledger consumption and native confirmation wiring, uncertainty consultation across both control stores for stage/restore, accounting, and controlled-volume measurement are the later batches and remain unimplemented.
