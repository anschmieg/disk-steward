# M1C purpose and bounded implementation sequence

M1A proved recoverable stage/restore on five app-created files. M1B broadens the editable, non-executable plan; human pilots remain open. M1C must prove actual removal separately from staging, preserving exact review, fresh identity checks, single-use authority and honest accounting. Its scope remains the five disposable fixtures; general metadata additions and user files cannot become targets.

The full sequence is stage → restore → fresh stage receipt → separately select exact staged receipts → irreversible review/native confirmation → revalidate → one-time ledger and durable intent → unlink only registered fixture slots → durable outcome → optional measured same-volume free-space observation. No timer, Trash enumeration, recursive delete, arbitrary path, all-staged default or model authority is permitted. Missing/changed/hard-linked targets and replaced parents block; uncertainty stops later children and never retries. Retain audit receipts, invalidate restore only for known permanent outcomes, and never infer recovered bytes from logical size or absent paths.

Before live service changes, prove allowlisted v1→v2 SQLite migration on disposable fixture databases. Existing session/manifests/receipt IDs, stage/restore attempts and completed/uncertain state must survive atomically. Unknown/malformed schemas remain untouched; fault injection rolls back partial table-copy/rebuild steps. A migration experiment is not a purge API and does not migrate the running app.

Later batches integrate the exact typed purge manifest and lifecycle/coordinator schema under the existing owner lease, then native review/confirmation/results and crash reconciliation. A controlled-volume measurement must establish any free-space claim; APFS snapshots, clones, open handles and concurrent writers prevent logical-byte inference. Residual same-user races and unsupported platforms must remain explicit. No user-file adapter is enabled by these fixtures.
