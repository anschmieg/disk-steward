# Batched in-memory subtree scanning

Continue R1.1/R1.2/R1.4/R1.5 and R6.5 from PR124, with main as eventual integration baseline. Explicit user initiation walks the currently held folder using independent no-follow directory streams; ordinary inventory paging, plan decisions and page bars remain independent. One retained job has exact observation/scan IDs, saved exclusion revision and physical bindings. Each sequential batch accepts a fresh cancellation attempt ID. Renderer requests expose no path or generic filesystem operation.

Bound traversal to 512 entries per batch, 65,536 entries total, 16 directory frames, cooperative two-second batch checks and 15-minute continuation eligibility. Expiry is checked when advancing, not an idle cleanup timer. Pause waits for the current batch boundary; Resume continues exact retained state. Cancel signals the active batch; uncertainty drops its resumable state. Explicit discard or successful scope replacement releases retained descriptors and deduplication state. App exit also releases it. Native filesystem calls are not forcibly interrupted.

Validate held and named directory identities before/after batches and saved exclusions before publishing evidence. Refuse stale IDs without consuming the current job. Changed bindings/exclusions, cancellation or deadline uncertainty cannot publish a successful batch. Preserve hidden/link/nonregular/cross-volume/managed/system/dataless boundaries and report incomplete coverage. Deduplicate file-object logical bytes across batches using device/inode and metadata consistency. Counts are historical metadata, not a consistent filesystem snapshot, occupied space or reclaimable space. No file contents, source writes, cleanup proposals or execution eligibility are added.

This is in-memory recursive continuation, not durable recursive recovery. The separate explicit one-folder paging checkpoint remains unchanged. Full selected-scope scan persistence, large-tree resource/performance measurements, cloud-provider behavior, native WebView/accessibility and roadmap MVP acceptance remain open. Unit fixtures and reduced-state limit tests do not close those gates. After actual MVP delivery, the final adversarial review/fixes/validation and automation disable/stop remain mandatory.
